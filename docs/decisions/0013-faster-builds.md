# 0013. Быстрые сборки приложения

- Статус: принято
- Дата: 2026-11-05

## Контекст

Сборка трёх платформ шла ~20 минут; время задавал macOS (компиляция Rust — 16 минут). Причины:

- кэш Rust почти не срабатывал: ветка видит кэш только свой и main, а на main сборок не было, поэтому
  каждая новая ветка начиналась с нуля;
- macOS собирался универсальным — две полные компиляции подряд (ARM и Intel) на Intel-машине;
- каждая сборка — с полной оптимизацией (LTO, одна единица компиляции);
- версии Rust-зависимостей не были закреплены: кэш хуже совпадал, а свежий Tauri однажды сломал сборку
  Android без изменений с нашей стороны.

## Решение

- **Сборка main после каждого слияния** (кроме правок только документации) — она же прогревает кэш.
  Кэш Rust (`Swatinem/rust-cache`) и Gradle (`gradle/actions/setup-gradle`) пишет только main,
  ветки только читают: кэш репозитория (10 ГБ) не забивается ветками, сохранение не тратит время веток.
- **Проверочная сборка — быстрые настройки компилятора**: без LTO, 16 единиц компиляции, `opt-level = 1`
  (переменные `CARGO_PROFILE_RELEASE_*` поверх `[profile.release]`). Релиз — как в `Cargo.toml`:
  LTO, одна единица компиляции, `opt-level = "s"`.
- **macOS**: проверочная сборка — только ARM (Mac владельца — Apple Silicon); релиз — универсальная.
- **`Cargo.lock` в репозитории**: сборки воспроизводимы, обновление Rust-зависимостей — отдельным
  изменением (`cargo update` в `apps/app/src-tauri`), с проверкой сборкой.

## Последствия

- Проверочная сборка приложения немного больше и медленнее релизной — для проверки на устройстве не важно.
- Релиз собирается со своим кэшем (другие настройки компилятора) — он прогревается релизами с main.
- Первая сборка после смены зависимостей — холодная, следующие — с кэшем.
